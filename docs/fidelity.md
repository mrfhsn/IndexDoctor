# Engine Fidelity & Sandbox Architecture

IndexDoctor provides in-engine index verification by executing queries against an authentic PostgreSQL 17 engine running inside WebAssembly (PGlite). This document describes the planner costing model, simulated row scaling, worker thread isolation, and the fidelity boundaries between the simulated sandbox and production hardware.

---

## 1. The Core Engine: PGlite in WASM

IndexDoctor uses [@electric-sql/pglite](https://github.com/electric-sql/pglite), which compiles the official PostgreSQL C codebase to WebAssembly using Emscripten.

- **PostgreSQL Version:** 17.x
- **Filesystem:** Emscripten in-memory virtual filesystem (MEMFS). No physical files are written to disk.
- **Portability:** Runs within the Cloud Run Node.js container process with zero external database dependencies.

Every candidate index generated by the Gemini model chain or the deterministic ESR heuristic is subjected to real PostgreSQL query analysis:

```sql
EXPLAIN (FORMAT JSON) <query>
```

If PostgreSQL does not choose the new index, or if the estimated cost does not decrease, IndexDoctor rejects or qualifies the recommendation (`not_improved`).

## 2. PostgreSQL Planner Cost Model

PostgreSQL's cost optimizer uses a mathematical model to estimate the work required to execute an execution plan:

$$\text{Cost}_{\text{seq}} = (\text{pages} \times \text{seq\_page\_cost}) + (\text{tuples} \times \text{cpu\_tuple\_cost}) + (\text{evals} \times \text{cpu\_operator\_cost})$$

$$\text{Cost}_{\text{idx}} = (\text{index\_pages} \times \text{random\_page\_cost}) + (\text{index\_tuples} \times \text{cpu\_index\_tuple\_cost}) + (\text{heap\_pages} \times \text{random\_page\_cost}) + \dots$$

Where PostgreSQL default weights are:

- `seq_page_cost`: `1.0`
- `random_page_cost`: `4.0`
- `cpu_tuple_cost`: `0.01`
- `cpu_index_tuple_cost`: `0.005`
- `cpu_operator_cost`: `0.0025`

### Why Small Tables Don't Use Indexes

On a table with only 50 rows, reading all 50 rows sequentially costs $\approx 1.0 \times 1 + 50 \times 0.01 = 1.5$. An index scan requires reading the index root page, leaf page, and then fetching the heap page via random I/O ($\approx 4.0 \times 3 = 12.0$). Therefore, on small tables, PostgreSQL **always** chooses a sequential scan, regardless of how good the index is.

## 3. Simulated Statistics Scaling (`UPDATE pg_class`)

To evaluate realistic indexing for production-scale tables without the latency and memory overhead of inserting hundreds of thousands of rows:

1. **Representative Seeding:** The sandbox seeds between 500 and 2,000 synthetic rows matching the column types and distributions.
2. **Catalog Scaling:** The sandbox runs `ANALYZE` to compute standard column histograms and null fractions, and then updates the PostgreSQL system catalog directly:
   ```sql
   UPDATE pg_class
   SET reltuples = 500000,
       relpages = CEIL((500000::float * avg_row_width) / 8192)
   WHERE relname = $1;
   ```
3. **Index Evaluation:** When candidate indexes are created (`CREATE INDEX ...`), PostgreSQL populates the index catalog and recalculates plan trees using the scaled tuple and page statistics.

This produces accurate plan transformations (e.g. `Seq Scan` $\to$ `Index Scan` $\to$ `Index Only Scan`) within **150–500 ms** per request.

## 4. Sandbox Security & Process Isolation

Untrusted user SQL must never compromise the container, exhaust resources, or interfere with other requests. IndexDoctor enforces four defense-in-depth layers:

```
[ Incoming Request ]
         │
         ▼
[ Layer 1: libpg-query AST Gate ]  ──(Rejects DDL/DML, COPY, DO, multiple statements)
         │
         ▼
[ Layer 2: Node.js Worker Thread ] ──(Isolated V8 heap; off the main event loop)
         │
         ▼
[ Layer 3: PGlite In-Memory MEMFS ]──(No system calls, no network, no host disk access)
         │
         ▼
[ Layer 4: Hard Timeouts & Recycle ](6-second SIGKILL abort, worker recycle every 300 jobs)
```

1. **Layer 1: AST SQL Gate:**
   - Pre-parses schema and query using PostgreSQL's native parser compiled to C/Node (`libpg-query-node`).
   - Allow-lists only `CreateStmt` (table definitions) and `SelectStmt` (read queries).
   - Rejects `COPY`, `DO`, `DROP`, `GRANT`, procedural execution, multi-statement injection, and unquoted exotic identifiers.
2. **Layer 2: Worker Thread Isolation:**
   - All PGlite operations execute inside a dedicated Node.js `worker_thread` (`src/server/sandbox/worker.ts`).
   - The main event loop remains non-blocking for HTTP ingress and health probes.
3. **Layer 3: Virtual Memory Filesystem:**
   - PGlite operates entirely within Emscripten's virtual memory filesystem. It cannot make outbound network requests or access host files.
4. **Layer 4: Timeouts & Worker Recycling:**
   - 6,000 ms hard job timeout. If a query hangs or triggers runaway WASM execution, the worker thread is terminated and respawned immediately.
   - Workers automatically recycle after 300 evaluations to prevent memory fragmentation.

## 5. Fidelity Boundaries (Honesty & Limits)

IndexDoctor is honest about what its simulation represents:

| Dimension             | Fidelity Level        | Notes                                                                                                                                                     |
| :-------------------- | :-------------------- | :-------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Planner Logic**     | **100% Authentic**    | Uses genuine PostgreSQL 17 cost equations, index scan rules, partial index predicate matching, and index-only scan visibility requirements.               |
| **Index Selection**   | **100% Authentic**    | If IndexDoctor claims an index is used, PostgreSQL's optimizer actively selected it in the generated plan.                                                |
| **Cost Reduction**    | **Planner Estimated** | Measures reduction in planner cost units, not execution wall-clock time on hardware.                                                                      |
| **Row Volume**        | **Simulated**         | Assumes 500,000 rows (`ASSUMED_ROW_COUNT`). On tables with billions of rows or complex join graphs, partitioned indexes or vacuuming patterns may differ. |
| **Data Distribution** | **Synthetic Sample**  | Seed data generates uniform/typical distributions. Highly skewed real-world distributions may alter selectivity.                                          |
| **Disk/Hardware I/O** | **Not Simulated**     | Does not simulate disk seek latency, RAID striping, SSD NVMe read caches, or OS page cache hit ratios.                                                    |

IndexDoctor is an **architectural index advisor**—it identifies missing indexes, validates column ordering (Equality $\to$ Sort $\to$ Range), and tests covering column (`INCLUDE`) eligibility using the genuine PostgreSQL planner.
